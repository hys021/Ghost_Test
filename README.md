# 👻 귀신 유형 테스트 (Ghost Type Test)

> 토스 미니앱 8월 챌린지 "미니앱과 함께하는 여름" 출품작
> 여름철 공포 콘텐츠와 MBTI를 결합한 심리테스트 서비스의 백엔드 레포지토리입니다.

밤늦게 교과서를 챙기러 몰래 학교에 잠입하는 스토리를 따라 8개의 질문에 답하면,
선택에 따라 MBTI가 계산되고 그에 대응하는 한국 귀신 유형이 결과로 출력됩니다.

---

## 📌 프로젝트 소개

- 사용자는 하나의 호러 스토리를 따라 8개의 질문에 답합니다.
- 각 선택지는 MBTI 4개 축(E/I, S/N, T/F, J/P)에 점수를 부여하며, 서버에서 이를 합산해 최종 MBTI를 계산합니다.
- 계산된 MBTI는 16종의 한국 귀신 캐릭터 중 하나와 1:1로 매칭되어 결과로 제공됩니다.
- 결과 화면에는 궁합(나와 잘 맞는 귀신 / 안 맞는 귀신), 학교별·전체 참여 랭킹 등 부가 콘텐츠를 함께 제공합니다.

## 🗂 아키텍처 개요

도메인(기능) 단위로 패키지를 분리하고, 각 패키지 내부는 계층(Entity / Repository / Service / Controller / DTO)별로 다시 구성했습니다.

```
com.example.test
├── ghost      # 귀신 유형 도감 (16종 MBTI-귀신 매핑, 궁합 정보)
├── story      # 스토리 질문/선택지, MBTI 계산 로직
├── history    # 테스트 이력 저장 및 결과 조회
├── school     # 학교 정보 (참여자 소속 학교)
└── ranking    # 귀신 유형별/학교별 참여 통계 및 랭킹
```

### 패키지 간 의존 관계

```
history  ──▶  ghost      (결과 조회 시 귀신 상세 정보 조인)
history  ──▶  story      (선택지 기반 MBTI 계산 로직 호출)
history  ──▶  school      (참여자 소속 학교 조회)

ranking  ──▶  history, ghost, school  (통계 집계)

story    ──▶  ghost      (계산된 MBTI로 귀신 매칭)
```

`ghost`, `story`는 다른 도메인에 의존하지 않는 독립적인 기반 도메인으로 설계하여,
`history`/`ranking`이 이를 조합해 사용하는 구조입니다.

## 🗃 ERD 요약

| 테이블 | 설명 |
|---|---|
| `ghost` | 16개 MBTI 유형과 1:1 대응되는 귀신 마스터 테이블 (이름, 설명, 이미지, 궁합 정보 포함) |
| `question` | 스토리를 구성하는 8개 질문 (상황 이미지 + 선택 후 반응 이미지) |
| `choice` | 각 질문의 선택지 (선택 시 반영되는 MBTI 4축 점수, 선택 후 반응 텍스트 포함) |
| `school` | 참여자 소속 학교 마스터 데이터 |
| `test_history` | 테스트 완료 이력 (학교, 결과 귀신, 완료 일시) — 공유 링크의 Key로 활용 |

### 설계 포인트

- **자기참조 FK**: `ghost.best_match_ghost_id` / `worst_match_ghost_id`는 같은 `ghost` 테이블의 다른 행을 참조하여, 귀신 간 궁합 관계를 표현합니다.
- **코드값과 표시값 분리**: `ghost_type`(내부 식별 코드)과 `name`(화면 표시용 이름)을 분리해, 표시 문구가 바뀌어도 데이터 정합성이 깨지지 않도록 설계했습니다.
- **정규화 기반 결과 조회**: `test_history`는 결과 귀신을 `ghost_id`(FK)로만 저장하고, 조회 시점에 최신 귀신 정보를 조인해서 가져오는 방식으로 설계했습니다.

## 🔌 API 명세

Base URL: `/api/v1`

| Method | Endpoint | 설명 |
|---|---|---|
| GET | `/questions` | 전체 질문 및 선택지 조회 (스토리 진행용, 한 번의 호출로 전체 데이터 수신) |

| GET | `/rankings` | 귀신 유형별 전체 순위/분포 조회 |
| GET | `/schools?keyword=` | 학교 검색 |
| GET | `/schools/{schoolId}/rankings` | 학교별 귀신 유형 순위/분포 조회 |

## 🧠 핵심 로직 — MBTI 계산

프론트엔드는 사용자가 선택한 `choiceId` 배열만 서버에 전달하며, MBTI 계산과 귀신 매칭은 전적으로 백엔드(`ResultCalculationService`)에서 수행합니다. 이는 클라이언트 측 조작으로 인한 결과 위변조를 방지하기 위한 설계입니다.

```
1. choiceId 배열로 선택지들의 4축 점수(E/I, S/N, T/F, J/P) 조회
2. 각 축 점수를 합산
3. 합산 결과의 부호로 MBTI 4글자 결정 (동점 시 E/N/T/J 기준 처리)
4. 계산된 MBTI로 매칭되는 귀신 조회 후 반환
```

## 🚀 프로젝트를 통해 배운 점

- 도메인 간 책임을 명확히 나누고, 계산 로직(`story`)과 저장 로직(`history`)을 분리해 각 팀원이 독립적으로 개발할 수 있는 구조를 설계했습니다.
- 자기참조 FK, 정규화/비정규화 트레이드오프 등 관계형 DB 설계 원칙을 실제 서비스 요구사항에 맞춰 적용했습니다.
- REST API 설계 시 클라이언트 신뢰성(결과값 위변조 방지)을 고려해 계산 책임의 위치를 결정했습니다.
